# 分析・編集の監査記録

広聴AIは、分析を実行するたびに入力、設定、モデル情報、中間結果、最終結果を非公開の監査領域へ保存します。管理画面で行うタイトル・説明、意見グループのラベル、表示設定、公開範囲の変更と、翻訳CLIの実行も記録します。異議申立てや行政の意思決定を管理する機能は含みません。

原文との対応や分析の正確性を調べる**内部監査用の記録**と、誰でも確認できる**公開監査用の資料**を分けています。内部記録は管理者だけが取得できます。公開資料は内部記録から項目と値を限定して生成し、管理者がプレビューを確認して公開したものだけを配信します。分析の実行やレポートの公開だけで、監査資料が自動公開されることはありません。

## 保存される情報

| 情報 | 内容 |
| --- | --- |
| 実行の識別 | 実行ID、対象レポート、操作の種類、UTCの開始・終了時刻、直前の操作の実行ID、成否 |
| 入力 | 実行時点のCSV。分析では保存したコピーを読み、その後の入力ファイルの変更を受けない |
| 設定 | 各処理のモデル・プロンプト本文、既定値を反映した設定、処理の有効・無効、実行計画。設定JSONは開始時と終了時に保存 |
| 実行環境 | analysis-coreとPythonの版、インストール済みパッケージの版、取得できる場合のGitコミットと未コミット変更の有無、分析コアのソースの指紋、許可リストにある実行環境設定 |
| モデルの応答情報 | 応答に含まれる場合のモデル名、モデルバージョン、リクエストID、fingerprint。本文や認証ヘッダーはこの記録には入れない |
| 処理の経過 | 各段階の開始、成功・失敗・スキップ、プラグインIDと版、解決済みの設定、入出力の対応、トークン使用量 |
| 成果物 | 抽出意見、元コメントとの対応表、埋め込み、クラスタ、ラベル、概要、有効にした分類・スコア、分析結果と公開用結果、翻訳、可視化設定 |
| 再利用 | スキップした段階の過去の処理記録。過去の記録に実行IDがあれば引き継ぐ。別レポートから再利用した場合はコピーした成果物も保存 |
| 変更前後 | 分析・編集の前後に存在した成果物。抽出を試みた分析では非公開の抽出診断も保存 |

元の成果物に認証情報が残っている場合は、設定から取り除いて保存し、対象ファイルに `redacted: true` を付けます。元のファイルはこの操作では変更しません。元コメントや抽出意見、プロンプトには個人情報が含まれ得るため、監査領域は公開しないでください。

保存対象は現在の標準処理の成果物と、ワークフローのプラグインが返すファイルです。CLIの確認用HTML、任意の隣接ファイル、通常のログ全体は対象外です。独自の処理を追加する場合は、必要な成果物をプラグインの `StepOutputs.artifacts` に含めます。

## ハッシュと版管理

モデル名、プロンプト、設定は、読んで比較できる値として保存します。個々の設定値をハッシュ化する必要はありません。入力CSV、最終結果、再利用するUMAPモデルにはSHA-256を付け、ファイルの取り違えを検出できます。分析コアにもソースファイルの指紋を付けます。

実行IDは日時とランダムなUUIDから生成します。完了済みの記録をアプリケーションが書き換えることはありません。再実行や編集では新しい実行IDを作り、直前の記録へリンクします。失敗した実行も残します。

通常の完了・例外・キーボード割り込みでは、最終マニフェストに `completed` または `failed` を記録します。強制終了などで最終マニフェストが作られなかった実行は `incomplete` のまま残ります。これは「現在実行中」という意味ではなく、最終状態の記録がないことを示します。実行途中にも開始記録と処理段階の記録を書き出します。

同じレポートへの分析・編集はプロセス間のファイルロックで排他制御します。ローカルファイルシステム上の複数プロセスに対応しますが、独立したディスクを持つ複数APIインスタンスの協調ロックではありません。同じレポートを処理するAPIは1インスタンスに集約するか、ロックをサポートする共有ファイルシステムを使ってください。

分析・編集中のレポートに別の編集を行うと、管理APIは409を返します。処理の完了後に再試行してください。

## 保存先

標準の `outputs/<report>/` に対して、監査記録はその外側の `audits/<report>/<run_id>/` に置きます。出力ベースディレクトリの名前が `outputs` 以外の場合は、隣の `<出力ベース名>.audits/` に保存します。

```text
pipeline/
  inputs/
  outputs/<report>/
  audits/<report>/<run_id>/
    started.json
    manifest.json
    config.json
    final_config.json
    inputs/
    before/
    steps/
    after/
    diagnostics/
    model_responses.jsonl
```

存在するデータだけを保存するため、すべての実行に同じファイルがあるとは限りません。`manifest.json` の `files` が、その実行の保存ファイル一覧です。監査記録は公開用の `public_result.json` に追加されず、通常のレポート成果物の同期・掃除にも含まれません。

保存先は `KOUCHOU_AUDIT_DIR` で変更できます。出力ディレクトリ配下は指定できません。同じ出力ツリーを扱うAPIと分析サブプロセスには同じ値を設定します。別のインストールには別の監査保存先を使ってください。Unixではディレクトリを0700、ファイルを0600で作成します。Windowsでは保存先ディレクトリのACLでも閲覧者を制限してください。

履歴は自動削除しません。レポートの論理削除後も残ります。入力・埋め込み・変更前後の成果物のコピーが蓄積するため、保存容量を監視し、組織の保存期間に合わせてバックアップ・廃棄を管理してください。保存失敗を成功として扱わず、実行や編集にエラーを返します。編集後の保存・同期失敗では、編集自体は反映されている場合があるため、状態を確認してから再試行してください。

## CLIで確認する

APIを使わず、監査領域を読める環境で確認できます。

```bash
kouchou-audit --report-dir outputs/example list
kouchou-audit --report-dir outputs/example show <run_id>
kouchou-audit --report-dir outputs/example verify <run_id>
kouchou-audit --report-dir outputs/example preview <run_id>
kouchou-audit --report-dir outputs/example export <run_id> --output public-audit.zip
kouchou-audit --report-dir outputs/example export <run_id> --audience internal --output internal-audit.zip
```

ソースから実行する場合は `python -m analysis_core.audit_cli` でも同じ操作ができます。`verify` は保存済みのハッシュを再計算し、ハッシュがないファイルは存在とサイズを確認します。不一致、欠落、未完了の記録では終了コード1を返します。サイズだけを確認したファイルの内容一致までは保証しません。検証時にpickleを読み込んで実行することはありません。

`preview` は公開候補のJSONと、その内容を特定するSHA-256を表示します。`export` の既定値は公開候補であり、公開用に生成した `audit.json` と、そのハッシュを記載した `manifest.json` だけをZIPに入れます。CLIからの取得は公開操作ではありません。外部へ渡す前に内容を確認してください。

**原文を含む従来の完全版ZIPには `--audience internal` の指定が必要です。** 完了または失敗の最終マニフェストと、そこに列挙されたファイルを取得できます。2回分の `config.json`、`steps/`、`before/`、`after/` を比較すると、条件と結果の変化を確認できます。このZIPは非公開データとして管理してください。どちらの形式でも、既存の出力ZIPは上書きしません。

## 管理APIで確認する

既存の管理者APIキーによる認証を使います。新しい権限や監査者アカウントは作成しません。公開APIキーでは取得できず、レスポンスには `Cache-Control: no-store` を付けます。

| メソッド・パス | 内容 |
| --- | --- |
| `GET /admin/reports/{slug}/audit?limit=50&offset=0` | 新しい順の履歴一覧。limitの上限は200 |
| `GET /admin/reports/{slug}/audit/{run_id}` | マニフェスト。未完了の場合は最後の開始・進捗記録 |
| `GET /admin/reports/{slug}/audit/{run_id}/verify` | 保存済みファイルの検証 |
| `GET /admin/reports/{slug}/audit/{run_id}/download` | 非公開監査データのZIP取得 |

管理APIキーには既存の編集権限もあります。第三者へ記録を渡す場合は、権限を持つ担当者がZIPを取得するか、監査領域への読み取り専用アクセスを用意してください。

## 公開監査資料の生成・公開・取り消し

公開ポリシーの版は `public-audit-v1` です。公開前の確認・承認に専用の管理画面はなく、CLIまたは管理APIでプレビューを取得します。
生成済みのZIPは、[独立した監査ビューア](independent-audit.md)で閲覧・比較・検証できます。ビューアは運用システムへの接続や管理者アカウントを必要としません。公開の承認操作は引き続き管理APIで行います。

Dockerで利用する場合、分析コアはAPIイメージに組み込まれているため、変更を反映するには `docker compose build api` で再ビルドし、APIコンテナを再作成する必要があります。

| 情報 | 公開する内容 |
| --- | --- |
| 実行の識別 | 内部記録と共通の実行ID、日時、操作の種類、成否。未承認の履歴や前の実行IDは掲載しない |
| 実行環境 | 分析コアの版とソースの指紋、形式を検証したGitコミット、変更の有無。パス・環境変数・依存パッケージ一覧は含めない |
| 分析条件 | 対応済みのプロバイダーと分析方式、公開ポリシーに登録されたモデル識別子、標準処理の数値・真偽値の設定 |
| プロンプト | 公開資料を生成する版の既定プロンプトと一致する場合はテンプレートID。一致しない本文は掲載せず `custom_or_unknown` と記録 |
| 処理件数 | 入力行数、抽出意見数、意見に対応する入力ID数・対応しない入力ID数を10件幅の範囲で掲載。個人や属性別の集計は作らない |
| 処理の経過 | 標準処理の成功・失敗・スキップ。エラー本文や独自プラグイン名は掲載しない |
| 変更 | 同じ操作の前後でモデル・プロンプト・設定・成果物などが変わったか。変更前後の本文は掲載しない |
| 加工の説明 | 公開ポリシーの版、除外する項目、検証できる範囲と限界 |

元コメント、抽出意見、ラベル、概要、任意のモデル名、属性名、URL、内部ファイルのハッシュ、埋め込みなどは含めません。公開レポートに含まれる文章も、そのまま監査資料へコピーしません。未知のフィールドやモデル識別子は内部に保持し、公開項目へ自動追加しません。

件数は23件なら20〜29件、0〜9件なら0〜9件という範囲になります。`null` は記録から確認できないことを示し、0件とは異なります。抽出が成功またはスキップで完了していない実行では、残っている過去の成果物を新しい抽出結果として数えません。タイトル編集・翻訳などの件数も、新しい分析結果とは扱いません。入力IDと意見の対応がない件数には、未処理・抽出対象外・意見なしなどが混在し得るため、誤抽出や失敗の件数を意味しません。

10件幅の表示は再識別の防止や差分プライバシーを保証しません。別の公開資料との照合や繰り返し公開による推測も考慮し、公開前に確認してください。公開資料だけでは、原文に忠実な抽出か、公平な分類かを検証できません。その確認には内部記録を利用します。

公開する手順は次のとおりです。管理APIには既存の管理者キーを `x-api-key` ヘッダーで渡します。

1. `GET /admin/reports/{slug}/audit/{run_id}/public-preview` で公開候補を取得する。内部記録が未完了、欠落、ハッシュ不一致の場合は生成を拒否する。
2. レスポンスの `document` を確認する。本文・独自モデル名を公開する機能はないため、これらを確認する監査には内部記録を使う。
3. `PUT /admin/reports/{slug}/audit/{run_id}/publication` に、確認した候補の `sha256` と `reviewed: true` を送る。

```json
{
  "sha256": "プレビューで取得した64桁のSHA-256",
  "reviewed": true
}
```

再生成した候補のハッシュが一致しなければ409を返し、再確認を求めます。`reviewed: true` は管理者による内容確認の記録であり、独立した監査者による検証やデジタル署名を意味しません。

公開できるのは `ready` かつ `public` のレポートです。`private`、`unlisted`、処理中、失敗、削除済みのレポートの公開資料は配信しません。取得のたびに現在の公開範囲を確認します。

| 認証不要のGET | 内容 |
| --- | --- |
| `/reports/{slug}/audit` | 承認して公開した履歴だけの一覧。`limit` と `offset` に対応 |
| `/reports/{slug}/audit/{run_id}` | 公開資料、資料のハッシュである `release_id`、公開日時 |
| `/reports/{slug}/audit/{run_id}/download` | 公開資料のZIP。原文を含むファイルは取得できない |

取り消す場合は管理APIの `DELETE /admin/reports/{slug}/audit/{run_id}/publication` を使います。内部記録と生成済みの版は保持したまま、公開APIから取得できなくなります。レポートを一時的に非公開にしただけの場合は、再び `public` にすると承認済み資料も取得可能になります。再公開させたくない資料は個別に公開を取り消してください。

公開APIは `Cache-Control: no-store` を返します。ただし、利用者が取得済みのZIPや別途保存したコピーを回収することはできません。

公開用の生成物と公開状態は、内部保存先の `publications/<run_id>/` に分けて保存します。Azureの場合も匿名アクセス無効のコンテナの `public-audits/<slug>/<run_id>/` に置き、APIが公開範囲を確認して返します。生成物の保存後に公開状態を保存し、失敗した操作は成功として返しません。Azureの公開状態は取得のたびに読み直すため、古いローカルの公開状態を使って取り消し済み資料を配信しません。公開・取り消しの操作は、同じローカルディスクを共有するプロセス間で排他制御します。

公開ZIPの `audit.json` に対して `sha256sum audit.json` を実行し、`manifest.json` の `files[0].sha256` と比較できます。これは配布資料の同一性を確認する検査であり、元データの正しさや運用者による同時改変がないことを証明するものではありません。

## Azure Blob Storage

`STORAGE_TYPE=azure_blob` の場合、監査データは `audits/<slug>/<run_id>/` プレフィックスに保存します。`AZURE_AUDIT_CONTAINER_NAME` を指定すると監査専用コンテナを使い、未指定なら既存のストレージコンテナを使います。いずれもコンテナの匿名アクセスが無効であることを確認し、有効な場合は保存を拒否します。コンテナの作成や権限変更は自動では行いません。

成果物を先にアップロードし、最終マニフェストを最後にアップロードします。監査データの同期に失敗した分析は `ready` になりません。失敗した分析についても監査データの同期を試みます。

再起動後は履歴のメタデータだけを取得し、ZIP取得・検証時に必要なファイルを復元します。ローカルに残る新しい記録を、古いリモートの記録で上書きしません。Azureを使わない構成では、監査領域を永続ボリュームに保存し、そのボリュームをバックアップしてください。

Azureとの同期はAPI経由の分析・編集で行います。分析CLI・翻訳CLIを単独で実行した場合はローカル保存のため、その監査領域も永続化・バックアップしてください。標準のCompose構成では `apps/api` がマウントされており、既定の保存先 `apps/api/broadlistening/pipeline/audits` もホストに残ります。保存先を変更した場合は、その場所の永続化と、Dockerのビルド対象からの除外を別途設定してください。

## 証明できる範囲

記録は、この版を導入した後にCLIまたは `PipelineOrchestrator` を通して実行した分析と、上記の編集から作られます。以前の実行の条件は復元できません。古い成果物を再利用した場合は、その時点のコピーを保存し、元の実行IDが不明であることを維持します。個々の分析関数を直接呼び出した処理や、外部からの手動ファイル編集を自動的に追跡するものではありません。

API提供のモデルでは、応答メタデータを保存しても重みの同一性を検証できません。情報が返されない場合は、モデルバージョンやリクエストIDを推定して埋めません。同じモデル・設定での再実行も、同じ結果になるとは限りません。

Git情報が取れない配布環境では、その項目はnullになります。`KOUCHOU_IMAGE_DIGEST` を設定した場合はコンテナの識別情報も保存しますが、これは運用者が与えた値であり、実行基盤による証明ではありません。分析・編集時の監査記録には署名や外部タイムスタンプを自動付与しないため、保存領域を管理できる者による記録とハッシュの同時改変までは検出できません。[配布時の署名](independent-audit.md#署名付き資料を作る)で受け渡し後の改変を検査できますが、実行時点から記録が変わっていないことの証明にはなりません。
